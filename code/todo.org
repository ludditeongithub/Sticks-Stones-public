Consider event-based triggers: instead of constant checks for time events, the time it takes will be calculated and sent to the calendar, which will then "schedule" it by adding it to the queue of recently incoming seconds, which constantly clicks down seconds/clicks, and when that second/click occurs, a data structure which contains all the scheduled events will be added to. At the very least, this reduces the number of checks down to 1 per second/click: checking if there are events scheduled for that second/click (if that clicks count is equal to the upcomingEvents vector). This works because if the event click will always be greater (farther in the future) then the current click, or it would have been taken off the stack.
This can vastly improve performance by calculating far into the future.
